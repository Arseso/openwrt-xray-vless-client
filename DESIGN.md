# luci-app-xvpn — VPN-клиент на xray для OpenWrt 24.10

Проектный документ: требования, принятые решения, архитектура, план проверки и идеи на будущее.

## 1. Требования

| # | Требование | Как закрыто |
|---|------------|-------------|
| R1 | LuCI-приложение для OpenWrt 24.10, удобное | Пакет `luci-app-xvpn`, раздел «Сервисы → XVPN», 5 вкладок, RU/EN |
| R2 | VPN-клиент | xray-core (`xray-core 25.1.30` из штатного фида 24.10) + TPROXY |
| R3 | Сам обновляет подписку | Демон `xvpnd` по таймеру, интервал из настроек или из заголовка `profile-update-interval` |
| R4 | Сам подключается к серверу | При старте берётся последний рабочий сервер, иначе — лучший по HTTP-пингу |
| R5 | Если подключение легло — переключение на лучший сервер по HTTP-пингу | Health-check каждые 30 с, после 3 неудач — тест всех серверов и переход на минимальный пинг |
| R6 | VPN для одной или нескольких точек доступа (порты, Wi-Fi сети) | Выбор сетей OpenWrt, отдельных LAN-портов (DSA) и отдельных SSID |
| R7 | Доп.: kill switch и защита DNS (выбрано пользователем) | Правила nft не снимаются при падении xray, рестарте и до старта сервиса при загрузке; при ошибке nft клиенты блокируются; DNS клиентов VPN перехватывается и идёт через туннель; IPv6 не утекает |

### Ответы пользователя (2026-10-26)
- Режим маршрутизации: **только полный туннель** — весь трафик выбранных точек доступа идёт в VPN.
- Протоколы: **всё, что умеет xray** — `vless://` (Reality, XTLS-Vision, XHTTP, WS, gRPC, HTTPUpgrade, mKCP), `vmess://`, `trojan://`, `ss://`.
- Устройство: **Xiaomi AX3000T** (MediaTek MT7981B, target `mediatek/filogic`, arch `aarch64_cortex-a53`, 128 МБ NAND, 256 МБ ОЗУ, порты `lan1..lan3` + `wan`, радио 2.4 и 5 ГГц).
- Доп. функции в v1: **kill switch + защита DNS**.

## 2. Ключевые решения

1. **Ядро — xray-core из фида.** В 24.10.4 есть `xray-core 25.1.30` (ipk ≈ 9.8 МБ, ≈ 25 МБ на флеше). На AX3000T места хватает. Geo-файлы (`v2ray-geoip`/`v2ray-geosite`) для полного туннеля не нужны и не ставятся. Путь к бинарю настраивается (`main.xray_bin`) — можно положить свежий xray с GitHub, если нужны функции новее 25.1.30 (например, VLESS `encryption`/ML-KEM).
2. **Бэкенд на ucode** — родной язык скриптов OpenWrt 24.10 (как в `luci-app-homeproxy`): модули `/usr/share/ucode/xvpn/*.uc`, скрипты `/usr/share/xvpn/{cli,xvpnd}.uc`.
3. **Перехват — nftables TPROXY** (TCP+UDP) в собственных таблицах `inet xvpn` и `bridge xvpn`. fw4 удаляет только свою таблицу `inet fw4`, поэтому наши таблицы переживают `fw4 reload`.
4. **Выбор сервера и failover — в нашем демоне, а не в балансировщике xray.** Каждый сервер — отдельный outbound, у каждого свой loopback SOCKS-инбаунд `127.0.0.1:20000+i` («тестовый порт»; занятые другими программами пропускаются, §6.5). TPROXY- и DNS-инбаунды маршрутизируются на активный outbound. Плюсы: прозрачные замеры для UI, полный контроль над логикой (проверка WAN, карантин, гистерезис). Переключение = перегенерация конфига + `reload` сервиса, procd перезапускает только xray (~1 с).
5. **HTTP-пинг** = `time_starttransfer` запроса `GET https://www.gstatic.com/generate_204` через SOCKS сервера (`curl -x socks5h://…`), ответ 204/200 обязателен. Тесты идут параллельно (по умолчанию 8 одновременно) через `uloop.process`.
6. **Кэш подписок на флеше** (`/etc/xvpn/subs/<id>.json`) — VPN поднимается после перезагрузки без доступа к серверу подписки. Пишем только при изменении содержимого (экономия ресурса NAND).
7. **Один пакет** `luci-app-xvpn` (`PKGARCH:=all`), собирается через `luci.mk`.

## 3. Архитектура

```
 Клиенты VPN-точек ─┐
  (SSID / lan-порт /│   bridge xvpn: метка CLIENT для выбранных портов и SSID
   сеть br-guest)   │   inet  xvpn : метка CLIENT для выбранных сетей
                    ▼
            prerouting mangle: CLIENT && не приватный dst && не DNS → TPROXY :12345 (+метка TPROXY)
            prerouting dstnat: CLIENT && dport 53                     → redirect :10853
            forward          : CLIENT && не приватный dst → reject (kill switch / IPv6 block)
                    ▼
   ┌──────────────── xray (procd instance) ─────────────────┐
   │ inbound tproxy :12345 ─┐                                │
   │ inbound dns    :10853 ─┼─► outbound srv-<активный>  ──► │──► VPN-сервер
   │   (dns_server — URL: dns-out → DNS-модуль xray, DoH)   │
   │ inbound test-i 127.0.0.1:20000+i ─► outbound srv-i      │
   │ inbound metrics 127.0.0.1:10085 (stats, /debug/vars)    │
   └─────────────────────────────────────────────────────────┘
                    ▲ reload (новый активный)
   ┌──────────── xvpnd (procd instance, ucode+uloop) ───────┐
   │ health-check, failover, re-rank, обновление подписок   │
   │ ubus-объект `xvpn`: status / test / select / update /   │
   │ reindex                                                 │
   └─────────────────────────────────────────────────────────┘
                    ▲ ubus
   LuCI (JS-вьюхи) ──► rpcd ucode-плагин `luci.xvpn` (офлайн-операции;
                       обновление подписок — через `ubus xvpn update`;
                       status / test / select — прокси к демону)
```

## 4. UCI-схема `/etc/config/xvpn`

```
config general 'main'
	option enabled '0'
	option xray_bin '/usr/bin/xray'
	option loglevel 'warning'          # debug|info|warning|error|none
	option tproxy_port '12345'
	option dns_port '10853'
	option api_port '10085'            # HTTP секции metrics xray (/debug/vars): статистика, живость xray
	option test_port_base '20000'
	option client_mark '0x01000000'    # метка «клиент VPN» (вне масок mwan3 0x3F00 и pbr 0x00ff0000)
	option tproxy_mark '0x02000000'    # метка для ip rule → table 
	option route_table '100'
	option sniffing '1'                # подменять IP на домен (http/tls/quic): многие серверы не пускают к IP

config access 'access'
	list network 'guest'               # целые сети OpenWrt
	list port 'lan2'                   # отдельные порты моста (DSA)
	list wifi 'wifinet2'               # секции wifi-iface (SSID); получают option ifname 'xvpn-apN' (§7.2)
	option killswitch '1'
	option ipv6 'block'                # block | tunnel
	option dns_hijack '1'
	option dns_server 'https://cloudflare-dns.com/dns-query'  # DNS клиентов через туннель: URL — DoH
	                                   # DNS-модулем xray (по домену), IP — пересылка на <IP>:53

config health 'health'
	option url 'https://www.gstatic.com/generate_204'
	option interval '30'               # с, проверка активного
	option timeout '5'                 # с, таймаут одного замера
	option fail_threshold '3'          # неудач подряд до failover
	option rank_interval '600'         # с, фоновый тест всех
	option auto_best '0'               # переходить на заметно более быстрый
	option hysteresis '150'            # мс, насколько быстрее должен быть новый
	option quarantine '300'            # с, «мёртвый» сервер не выбирается
	option concurrency '4'             # параллельных замеров в тесте всех, 1..8 (память, §6.4)
	list no_auto 'a1b2c3d4'            # id серверов вне автоподбора (§6.6); нет в конфиге по умолчанию

config subscription
	option name 'Мой VPN'
	option enabled '1'
	option url 'https://example.com/sub/xxxx'
	option user_agent 'v2rayN/7.0'     # провайдеры (Marzban/Remnawave/3x-ui) выбирают формат по UA
	option update_interval '12'        # часы; 0 = из profile-update-interval или 12
	option include ''                  # regex по имени сервера
	option exclude ''
	option via_tunnel '1'              # качать через активный сервер, при неудаче — напрямую

config manual 'manual'
	list link 'vless://…#Мой сервер'
```

## 5. Подписки и ссылки

- Загрузка: `curl -sSL --max-time 30 -A <UA> -D <headers> -o <body>`; через туннель — `-x socks5h://127.0.0.1:<тестовый порт активного>`, при неудаче — напрямую.
- Форматы тела: base64 (обычный и URL-safe, без паддинга) списка ссылок; plain-список; xray-JSON (массив полных конфигов или один конфиг — берётся первый outbound с протоколом vless/vmess/trojan/shadowsocks, имя из `remarks`). Clash YAML и sing-box JSON не поддерживаются → понятная ошибка «смените User-Agent».
- Заголовки: `subscription-userinfo` (upload/download/total/expire → показываем трафик и срок), `profile-update-interval`, `profile-title` (в т.ч. `base64:`).
- Ссылки → xray outbound:
  - `vless://uuid@host:port?type=&security=&flow=&sni=&fp=&alpn=&pbk=&sid=&spx=&host=&path=&serviceName=&mode=&headerType=&seed=&extra=&allowInsecure=#name`
  - `vmess://base64(JSON v2rayN)`
  - `trojan://password@host:port?…` (security по умолчанию tls)
  - `ss://base64(method:password)@host:port#name` (SIP002) и legacy `ss://base64(method:password@host:port)`; плагины (obfs/v2ray-plugin) — пропуск.
  - Транспорты: `tcp` (+ http-обфускация), `ws`, `grpc`, `xhttp`/`splithttp`, `httpupgrade`, `kcp`. Не поддерживаемые xray 25.1.30 (`h2`/`http`, `quic`) и протоколы (`hysteria2`, `tuic`) — пропускаются со счётчиком «пропущено».
- id сервера = FNV-1a от (источник: id подписки или `manual`, протокол, имя, учётка: uuid или пароль). Адреса и порта в нём нет: некоторые подписки при каждом скачивании выдают другой хост того же сервера (#49), а id от адреса выкидывал бы такой сервер из индекса и сбивал выбор активного. У ссылки без имени (в UI её имя — `адрес:порт`) имя в id пустое. Серверы одного источника с одинаковыми протоколом, именем и учёткой различаются по порядку в подписке (второй получает id от той же строки с `|2` и т. д.); если такие поменяются местами, замеры и карантин перейдут к другому серверу до следующего теста. Id считается в `all_servers` по кэшу до фильтров include/exclude, поэтому смена фильтра серверы не перенумеровывает. Сервер, у которого в имени меняющийся счётчик (информеры вроде «Трафик: …»), при каждом изменении имени — новый сервер.
- hash сервера = FNV-1a от соединения (протокол, адрес, порт, учётка, streamSettings) — так раньше считался id; он есть и в индексе. По нему отбрасываются дубликаты (тот же сервер в двух подписках или в подписке и ручных ссылках). По нему же `build_index` находит выбранный сервер, если его id в индексе нет: hash берётся из прежнего индекса (сервер переименован, подписку удалили и добавили заново, выключили подписку, а тот же сервер есть в другой), а для id из версий до #49 им служит сам id. Найденный так выбор `cli.uc generate` переписывает в `/etc/xvpn/active` под новым id и пишет `moved_from` в индекс, а демон по `moved_from` принимает его без нового выбора. Поэтому обновление пакета выбор не сбрасывает; сбрасываются только замеры и карантин (они по id и замеряются заново). Кэши до #49 хранят hash в поле `id`; `assign_ids` собирает записи с фиксированным порядком полей, так что старый кэш сравнивается с новым без ложных изменений. Фильтры include/exclude — регулярки по имени, без учёта регистра.

## 6. Логика демона xvpnd

1. Старт: загрузить индекс; если активный неизвестен — сразу тест всех и выбор лучшего. До синхронизации времени (NTP) серверы не тестируются и не уходят в карантин (п. 6.4).
2. Каждые `interval` с — HTTP-пинг активного через его тестовый порт.
3. Неудачная проверка → сначала проверка самого xray (п. 6.2): если не работает он, сервер не виноват — неудача не считается. `fail_threshold` неудач подряд → проверка прямого интернета (тот же URL без прокси):
   - нет прямого интернета → состояние `wan_down`, серверы не трогаем, ждём;
   - есть → `failover`: активный в карантин, тест всех, переход на минимальный пинг. Если живых нет и xray работает → `no_servers`, повтор на каждом тике; если не работает xray → `xray_down`, решение откладывается до его восстановления.
4. Каждые `rank_interval` с — фоновый тест всех (для UI). При `auto_best=1` переход, только если лучший быстрее текущего более чем на `hysteresis` мс.
5. Каждые 5 мин — проверка, не пора ли обновить подписки; обновление идёт отдельным процессом (`cli.uc update <sid…>`). `reload` (код 0) нужен, если серверы появились или пропали (в т. ч. сменился uuid или имя) или изменился активный: тот, что в индексе (его гоняет xray), или выбранный в `/etc/xvpn/active` — по id или hash. Если изменились только другие серверы (обычно ротация хоста, #49) или их порядок, reload не делается: он перезапустил бы xray и оборвал соединения клиентов. Вместо этого ставится `/var/run/xvpn/stale` (код 2). До ближайшего reload xray ходит к таким серверам по старым адресам; их пинги и адреса в `status` — старые (индекс описывает работающий конфиг). Ближайший reload будет при переключении (failover, ручной выбор), при реальном изменении списка или при внешнем reload. Выбор лучшего (`choose_best`: старт, failover, отложенный выбор) при `stale` сначала делает reload и выбирает уже по новым адресам; `rank`, нашедший более быстрый сервер при `stale`, не переключается по старым замерам, а зовёт `choose_best`. Если reload сейчас не проходит (`reload_error`), выбор идёт без него; отложенный до reload выбор (`choose_pending`) при неудачном reload выполняется сразу. Изменения только profile-title/интервала/userinfo reload не вызывают.
6. Ручной выбор сервера в UI (`xvpn.select`) — сразу переключает; дальше работает обычный failover. Сервер вне автоподбора выбирается вручную так же (§6.6).
7. Kill switch выключен и живых серверов нет → правила TPROXY снимаются (клиенты идут напрямую) до появления живого сервера.

### 6.1 Обновления и устаревший индекс
- **Одна точка входа.** Подписки обновляет только демон: rpcd `luci.xvpn update` вызывает `ubus xvpn update`. Без демона (сервис выключен или procd его перезапускает) rpcd сам запускает `cli.uc update` и, если сервис запущен, `reload`. Взаимоисключение — в `cli.uc update`: лок `/var/run/xvpn/updating` берётся атомарным `symlink` на свой pid, лок умершего процесса снимается. `updating` в `status` демона и в `luci.xvpn subscriptions` — это один и тот же лок.
- **Индекс перечитывается при любом reload.** Сервис перезагружают и мимо демона (rpcd, UCI-триггеры `wireless`/`network`). `service_started()` в `init.d/xvpn` после `fw-apply` и передачи инстансов procd вызывает `ubus xvpn reindex` — пауза на перезапуск xray отсчитывается от этого момента, а сброс passthrough не опережает `fw-apply`; кроме того, демон сравнивает содержимое файла на каждом `check` и `status`. Изменение, сделанное не демоном, обрабатывается так же, как после своего `reload`: 3 с на перезапуск xray, затем синхронизация (активный пропал или xray ведёт трафик не туда → выбор лучшего, иначе — проверка активного).
- **Поколения замеров.** Тестовые порты позиционные (`20000+i`, занятые пропускаются — §6.5), поэтому каждое изменение индекса и каждый `reload` демона увеличивают номер поколения. Замер принимается, только если за время замера поколение не менялось и xray не перезапускался; иначе он отбрасывается, а в тесте всех — повторяется по новому индексу. Порт берётся по id сервера в момент запуска замера; замеры и карантин удалённых серверов удаляются.

### 6.2 xray не работает ≠ сервер недоступен
Если xray упал, завис, не стартует (битый конфиг или бинарь, занятый порт, OOM) или крутится в respawn, падают пинги всех серверов, хотя прямой интернет есть. Поэтому перед тем как засчитать неудачу серверу, демон проверяет xray:
- инстанс `xray` запущен по `ubus call service list '{"name":"xvpn"}'` и не остановлен (`T` в `/proc/<pid>/stat`, `kill -STOP`). Если procd не ответил (таймаут ubus 2 с), состояние xray неизвестно: неудача не засчитывается ни xray, ни серверу;
- xray отвечает на своём api-порту (`127.0.0.1:api_port`, dokodemo-door → HTTP секции `metrics`): ответ даёт сам xray, без удалённого сервера. curl: 7 (connection refused) — xray не слушает, 28 (таймаут) — завис, любой другой код — живой;
- тестовый SOCKS-порт не отказал в соединении (curl 7 на пинге; таймаут и ошибки TLS — это уже сервер).

Если xray не работает: серверы в карантин не идут (карантин активного снимается), passthrough не включается, замер не записывается. В тесте всех неудачи записываются (`ms: -1`), только если после теста xray работает; отказ тестового порта не записывается никогда. Первые `XRAY_GRACE` = 10 с — терпение (старт xray, respawn procd), состояние не меняется; затем `xray_down`. В `last_error` — что не так и, где это помогает, подробности, пересчитанные на каждой проверке: отсутствующий бинарь называется прямо; если инстанса нет (`cli.uc generate` не запустил xray) — вывод `xray run -test` (асинхронно, зависший бинарь убивается через 5 с); если xray не запущен или не слушает — последние строки его лога (procd пишет stdout/stderr в logd под именем бинаря; строки запущенного pid, иначе последнего процесса с этим именем, без баннера, `started` и предупреждений `deprecated`). У остановленного и зависшего xray строк лога нет. Демон сам перезапускает xray: до `XRAY_RESTARTS` = 3 раз с паузой `XRAY_RETRY` = 15 с, затем раз в `XRAY_BACKOFF` = 10 мин или сразу, как только бинарь изменился (inode, размер, mtime). Зависший перезапускается через `ubus call service signal` (SIGKILL, procd поднимает его заново), не запущенный — `reload` сервиса. После трёх неудач в `last_error` — «3 restarts did not help…». Как только xray снова отвечает, счётчик (`xray_restarts` в `status`) сбрасывается, отложенный выбор сервера выполняется, а ручной выбор (`select`) его отменяет. Во время reload и паузы после него (п. 6.1) проверок нет, так что перезапускающийся xray за отказ не считается. Отсчёты терпения и пауз идут по монотонным часам, их не сбивает NTP при загрузке.

`cli.uc generate` отбрасывает серверы, которые xray отвергает, но если xray отвергает и конфиг без серверов, сломан он сам: список серверов сохраняется (а не «нет серверов»), xray не запускается, демон показывает `xray_down` с выводом `xray run -test`. Новый конфиг пишется в `config.new.json` (xray определяет формат по расширению) и заменяет `config.json` вместе с `index.json` только в конце: `generate`, убитый посередине (OOM, демон), оставляет конфиг, с которым работает xray, и его индекс. Время ограничено (в busybox OpenWrt нет `timeout`, поэтому через uloop): `-test` полного конфига — 40 с (на сотнях outbound он законно долгий), конфига без серверов и одного сервера — 15 с, на весь `generate` — `generate_budget` = 240 с. Зависший `-test` убивается вместе с потомками и считается отказом: зависший бинарь даёт `xray_down` через 40 + 15 = 55 с. Перебор серверов по одному на медленном роутере может не уложиться в 240 с: тогда непроверенные серверы отбрасываются (в лог — сколько), а конфиг собирается из уже проверенных, на последний `-test` полного конфига оставляется 40 с. Если не уложиться и так (бюджет меньше первых тестов), `generate` выходит с кодом 5, `init.d` оставляет xray на текущем конфиге, а демон считает reload неудачным (п. 6.3). Код выхода `-test` сохраняет `sh` в файл: `uloop.process` отдаёт 0 и для процесса, убитого сигналом, поэтому xray, убитый OOM, — отказ, а не успех. Какие `-test` вообще запускаются, решают запомненные вердикты (§6.4).

### 6.3 Зависший reload и сторож
`reload` демона (`init.d/xvpn reload`) может зависнуть: лок сервиса procd держит кто-то другой, procd не отвечает. Пока идёт reload, проверок нет (п. 6.1), а `select` отвечает `busy`. Жёсткий таймаут убивал бы законно долгий `generate` (п. 6.2), поэтому демон раз в 10 с смотрит на прогресс: процессы reload и их время CPU, а также другого `init.d/xvpn` (rpcd, UCI-триггеры), который держит лок procd. Ожидание лока или зависшего procd ничего из этого не меняет. Если прогресса нет `reload_idle` = 60 с или reload идёт дольше `generate_budget + 120` = 360 с с момента, когда он получил лок procd (в его дереве появился `cli.uc`: ожидание лока за чужим законным reload не считается), он убивается вместе со всем, что запустил: дерево по ppid из `/proc` сначала останавливается SIGSTOP (чтобы никто не успел породить новых потомков, пока его обходят) и обходится повторно, потом SIGKILL. Оставшийся потомок держал бы лок procd (fd 1000 init-скриптов); по той же причине фоновый `ifnames-wait` запускается без fd 1000. Неудачным считается и reload, который не удалось запустить, и убитый сигналом (OOM): код выхода `init.d` сохраняет `sh` в файл. И reload, в котором `generate` не уложился в бюджет и оставил прежний конфиг (код 5, причина в `/var/run/xvpn/generate_error`). `reload_idle` меньше `-test` полного конфига (40 с) ставить нельзя: долгий `-test` без расхода CPU (ожидание ввода-вывода) выглядел бы зависанием; значения меньше нужны только itest с быстрыми конфигами.

После неудачного reload xray, скорее всего, работает со старым конфигом (`generate` заменяет конфиг и индекс только в конце), поэтому проверки активного сервера, failover и passthrough идут как обычно. Активным считается сервер индекса, с которым работает xray: переключение (`select`, failover) не выполнено, пока reload его не применил, а `ACTIVE_FILE` хранит его для следующей попытки. `status` при этом показывает `error` с причиной (`reload made no progress for 60 s and was killed`), как при `fw_error`. Ручной `test` и фоновый `rank` не выполняются: тестовые порты могут не совпадать с тем, что запущено. Failover идёт через тест всех (`choose_best`) и в этом состоянии: без него клиенты остались бы на мёртвом сервере, а замеры по индексу, который совпадает с работающим конфигом, верны. Идущий тест всех прерывается: отложенный выбор сервера выполнится по `xray_check`, отказ тестового порта при этом сохраняется (только для выбора сервера, не для `rank` и ручного теста). Повтор reload идёт по своему таймеру раз в `reload_retry` = 30 с (не с тика проверки: при большом `interval` было бы редко); `reload_idle`, `reload_retry` и `generate_budget` — скрытые опции секции `health` (их нет в конфиге по умолчанию), itest уменьшает первые две, чтобы не ждать минутами; `select`, failover и обновление подписок пробуют сразу, reload мимо демона (`reindex` из `service_started()`) тоже снимает ошибку.

Сторож — последняя линия на случай флага, оставшегося по непредусмотренному пути: раз в 30 с демон смотрит, когда проверка последний раз прошла мимо `testing`/`reloading` (или пришёл результат замера в тесте всех, или закончилась пауза после reload). Если это было дольше `3 × interval + generate_budget + 150 с` назад (дольше любого законного reload) — в лог `health checks stalled…`, reload (если был) убивается, флаги и пауза сбрасываются, тест прерывается, поколение меняется, затем проверка или отложенный reload. Сам uloop сторож не спасает: если цикл заблокирован синхронным вызовом, помогает только respawn procd. Поэтому демон не ждёт logd: `logger` и `logread` блокируются, пока logd стоит. Лог демона идёт в фоне через один `logger` за раз (накопившиеся сообщения — одной пачкой через stdin). Застрявший с logd `logger` не убивается, иначе его сообщения потерялись бы: они придут, когда logd оживёт. В очереди не больше 100 сообщений, лишние отбрасываются с записью об их числе; при выходе (SIGTERM) очередь отправляется синхронно. Строки лога xray для `last_error` (п. 6.2) читает асинхронный `logread` с таймаутом 5 с: причина обновляется, когда он закончит. Синхронными остались вызовы ubus к procd (`service list`, таймаут 2 с) и короткие `kill`.

### 6.4 Время до синхронизации NTP
У AX3000T нет RTC: после загрузки часы стоят по `sysfixtime` (самый новый файл в `/etc`), пока sysntpd (busybox `ntpd`) их не выставит. VMess (AEAD) отвергает расхождение больше ~2 минут, Shadowsocks 2022 — ~30 с, REALITY с `maxTimeDiff` и TLS — сильное; в это время неудачи серверов говорят о часах, а не о серверах, и обычная логика отправила бы в карантин все серверы сразу после загрузки.
- **Признак синхронизации.** busybox `ntpd` вызывает `ntpd-hotplug`, тот — `hotplug.d/ntp` с `ACTION` (`step`, `stratum`, `periodic`, `unsync`) и `stratum` в окружении. `hotplug.d/ntp/50-xvpn` на `step` или `stratum`/`periodic` со `stratum` < 16 создаёт `/var/run/xvpn/time_synced` и дёргает `ubus xvpn check`. Флаг на tmpfs: живёт до перезагрузки, так что перезапущенный демон не ждёт заново. `ubus call system info` синхронизацию не показывает, а флаг ядра (`adjtimex`) из ucode не прочитать. Пакет, поставленный на работающий роутер (`uci-defaults` при uptime > 5 мин), создаёт флаг сам: NTP отработал раньше, чем появился hotplug-скрипт (да и `opkg` по HTTPS с неверными часами не работает).
- **Когда ждать.** При старте демона, если флага нет, `health.time_wait` > 0 и NTP включён: секция `system.ntp` (`timeserver`) с `enabled` не ложным (`0`, `false`, `no`, `off`, `disabled`), серверами или не ложным `use_dhcp` и `sysntpd enabled` — те же условия, при которых sysntpd запускает `ntpd`. NTP выключен — ждать нечего. Другой NTP-клиент (chrony) hotplug не шлёт: ожидание кончится по таймауту.
- **Ожидание.** Состояние `waiting_time`, не дольше `time_wait` = 120 с с первого старта демона после загрузки (скрытая опция `health`, 0 — не ждать): срок по монотонным часам хранится в `/var/run/xvpn/time_wait`, так что перезапуск демона (`uci commit xvpn`, respawn) ожидание заново не начинает. Затем в лог `no NTP sync in … s` и дальше по обычным правилам с часами как есть. Пока ждём, нет карантина, failover, теста всех и `rank`, ручной `test` отвечает `busy` (иначе все серверы получили бы `-1`). Выбор сервера (`choose_best` при первом старте, после обновления подписки) откладывается и выполняется на первой проверке после синхронизации. Автоматические обновления подписок (при старте без серверов и каждые 5 мин) тоже ждут — TLS с отстающими часами не проходит — и запускаются сразу после синхронизации; ручное обновление из LuCI идёт сразу. Активный сервер проверяется на каждом `interval`: отвечает — состояние `connected` (часы верны, просто флага нет — например, пакет поставлен в первые минуты после загрузки), нет — `waiting_time`, неудачи не считаются (`fails`). xray при этом не проверяется (`xray_check`, перезапуски демона из п. 6.2 не работают — упавший xray поднимает только respawn procd), его проверка начинается после ожидания. Клиенты VPN: с kill switch — через активный сервер (не отвечает — без интернета, напрямую нельзя); без kill switch — passthrough, пока активный не отвечает или его нет, как при «нет живых серверов» (§6, п. 7), и обратно, как только ответит. Пускать клиентов напрямую всё ожидание было бы утечкой при работающем сервере (VLESS без REALITY от часов не зависит), а ждать с блоком без kill switch — лишать интернета до 2 минут.
- Трафик самого роутера (NTP в том числе) идёт напрямую, мимо VPN, поэтому синхронизация от VPN не зависит.

ubus `xvpn`: `status` → `{state, active, since, fails, servers:[{id,name,proto,sub,latency,tested,quarantined,auto}], testing, tests, updating, passthrough, last_error, last_switch, last_test, xray_restarts}`; `test` (запустить тест всех или присоединиться к идущему; ответ `{ok, run}`: этот прогон закончен, когда `status.tests >= run`); `select {id}`; `set_auto {id, auto}` (§6.6); `update {sid?}` (обновить подписки, `{ok:false, error:"busy"}`, если обновление уже идёт); `check` (проверить сейчас); `reindex` (перечитать индекс; вызывается из `service_started()` в `init.d/xvpn` после каждого start/reload).

Состояния (`state` в `status`; текст причины — в `last_error`):

| Состояние | Значение |
|-----------|----------|
| `starting` | демон только запущен, проверки ещё не было |
| `waiting_time` | часы ещё не выставлены NTP (п. 6.4): серверы не в карантине, переключений нет |
| `connected` | активный сервер отвечает |
| `degraded` | были неудачи, порог `fail_threshold` не достигнут |
| `failover` | активный в карантине, идёт тест всех и переход |
| `wan_down` | нет прямого интернета, серверы не трогаем |
| `no_servers` | в подписках нет серверов или ни один не отвечает (xray при этом работает) |
| `xray_down` | не работает сам xray (п. 6.2): серверы не в карантине, passthrough не включается; в `last_error` — причина и последние строки xray, `xray_restarts` — сколько перезапусков сделал демон |
| `error` | nft не принял правила, клиенты заблокированы; или reload сервиса завис, не запустился либо был убит (п. 6.3): проверки идут, reload повторяется каждые 30 с |

### 6.4 Память (256 МБ)
На AX3000T 256 МБ ОЗУ, OOM-killer выбирает самый большой процесс — xray, и VPN рвётся у всех клиентов. Поэтому рядом с работающим xray не запускается второй без нужды, а сам xray держится в рамках:
- **Статистика без бинаря.** Раньше `stats` запускал `xray api statsquery` (второй процесс xray на 25+ МБ) на каждый опрос вкладки. Теперь в конфиге секция `metrics` (expvar: `stats.outbound.<tag>.uplink/downlink`, ~5–12 КБ JSON при 20–200 серверах); у `metrics` в 25.1.30 нет `listen` (появился позже), поэтому её отдаёт dokodemo-inbound на `127.0.0.1:api_port` с маршрутом в outbound `metrics` — как раньше gRPC API, который больше не нужен и убран. rpcd читает его curl'ом (`-m 1`): открытая вкладка «Статус» не запускает ни одного процесса xray (проверяет itest, обёрткой `xray_bin`, которая считает запуски). На том же порту демон проверяет живость xray (§6.2): ответ HTTP 404 на `/` — живой.
- **`xray run -test` — один раз на список серверов.** `-test` — это второй xray со всеми outbound и inbound, по памяти как работающий. `generate` запоминает вердикты в `/var/etc/xvpn/tested.json`: сигнатура бинаря (inode, размер, mtime — другой бинарь может судить иначе), хэш настроек `main` и `access` (всё, кроме серверов, что попадает в конфиг: порты, DNS, sniffing), ключ набора серверов, чей полный конфиг xray принял (хэш отсортированных ключей outbound), и для каждого сервера FNV-1a + длина JSON его outbound → принят / отвергнут. Другой бинарь или другие настройки — всё заново, в том числе отвергнутые серверы. Если набор серверов тот же, что принят последним, `-test` не запускается вовсе — это reload после выбора сервера, смены Wi-Fi, рестарт. Изменился набор (обновление подписки, ручные ссылки) — один `-test` полного конфига, и только его успех запоминает набор; серверы, принятые порознь (в переборе или в разных запусках), вместе всё равно проходят полный тест. Отвергнут — прежний перебор (§6.2), но по одному тестируются только серверы без вердикта; отвергнутые раньше отбрасываются без теста (в лог — «rejected … earlier»). Запоминается только вердикт xray о конфиге — успех или код 23 (ошибка конфига; проверено на 25.1.30): зависший, убитый сигналом (OOM), упавший в рантайме Go (код 2) `-test` не записывается, как и тест сервера, чей файл записался не целиком (заполненный tmpfs — xray отверг бы обрезанный JSON с тем же 23). Вердикты записываются и при выходе по бюджету; серверы, пропавшие из подписок, из файла удаляются. Файл в `/var`: после перезагрузки всё тестируется один раз заново. Гарантии §6.2 не меняются: бюджет, атомарная замена `config.json`/`index.json`, битый `xray_bin` (другая сигнатура → полный тест → отказ конфига без серверов → `xray_down`).
- **GC xray.** `init.d` запускает xray (и `-test` в `generate`) с `GOMEMLIMIT=80MiB GOGC=50` — скрытые опции `main.gomemlimit` и `main.gogc` (нет в конфиге по умолчанию). Значение, которое Go не разберёт (`80MB`, `80M`), остановило бы xray при запуске (exit 2), поэтому `init.d` принимает только `<число>[B|KiB|MiB|GiB|TiB]` / `off` и число / `off` для `gogc`, иначе пишет в лог и берёт значение по умолчанию. Те же переменные получает демон для своего `xray run -test` (§6.2). Без них Go растит кучу до 2× живой и отдаёт память ОС медленно: под нагрузкой RSS xray в контейнере (с буферами amd64, см. ниже) доходил до 270 МБ и не возвращался. `GOGC=50` держит кучу в 1,5× живой, `GOMEMLIMIT` — мягкий предел: ближе к нему GC работает чаще и память быстрее возвращается ОС. Живую кучу он не ограничивает (при нехватке GC занимает до 50 % CPU, но не падает). 80 МБ — из бюджета: OpenWrt с LuCI после загрузки занимает ~60–70 МБ из ~230 доступных, на `-test` при `generate` нужно ~30 МБ, на curl-замеры, rpcd и uhttpd ~10–15 МБ — остаток ~120 МБ, предел оставляет запас на превышение. На AX3000T `GOGC=50` вдвое снижает пик под нагрузкой без потери скорости, а `GOGC=100` подходит вплотную к пределу 80 МБ (замер ниже) — по умолчанию оставлен 50.
- **Параллельность замеров** (`health.concurrency`) по умолчанию 4, не больше 8: каждый замер — curl (~2–4 МБ, в основном общие библиотеки) и соединение в xray с буферами TLS/Reality.

Замер RSS xray 25.1.30 в контейнере `openwrt/rootfs:x86-64-24.10.4` (go1.23.12; `VmRSS`/`VmHWM` из `/proc/<pid>/status`). Серверы — смесь VLESS Reality+Vision, XHTTP+Reality и WS+TLS, удалённые адреса недоступны; «после теста» — после HTTP-пинга через все тестовые порты по 4 параллельно. ### 6.5 IPv6 и занятые порты
`cli.uc generate` один раз перед сборкой смотрит, что есть на роутере (`host.uc`):
- **IPv6.** Он выключен, если `/proc/net/if_inet6` пуст или его нет (при включённом IPv6 у `lo` всегда есть `::1`), либо `net.ipv6.conf.all.disable_ipv6 = 1`. Тогда инбаунды `tproxy` и `dns-in` слушают `0.0.0.0` (в ядре без IPv6 или с `ipv6.disable=1` bind на `::` не проходит; при `disable_ipv6 = 1` проходит, но IPv6-трафика нет); DNS-модуль отвечает только A (`UseIPv4`). `ipv6 = tunnel` при этом — ошибка конфигурации: она пишется в индекс (`config_error`), `status` показывает `error` с причиной, а IPv4 идёт в туннель как обычно. Правила nft в этом случае строятся как для `block`: без `tproxy ip6`, `ip -6 rule`/`route` не добавляются (маршрут `local default dev lo` ядро при `disable_ipv6` отвергает). Флаг IPv6 правила берут из индекса, а не проверяют заново: правила совпадают с тем, на чём слушает работающий xray, даже если IPv6 включили после `generate`.
- **Порты.** Занятые порты читаются из `/proc/net/{tcp,tcp6,udp,udp6}`: TCP — только в состоянии LISTEN (соединение с порта не мешает bind с `SO_REUSEADDR`), UDP — все. Сокеты нашего работающего xray (процесс с `run` и `/var/etc/xvpn/config.json` в argv, по inode из `/proc/<pid>/fd`) не считаются: новый конфиг займёт эти порты после перезапуска. Тестовые порты выдаются подряд от `test_port_base`, занятые другими программами и совпадающие с основными пропускаются; индекс хранит фактический порт каждого сервера, демон берёт его оттуда. Если занят `tproxy_port`, `dns_port` (TCP или UDP) или `api_port` (TCP), xray с новым конфигом не стартовал бы: `generate` выходит с кодом 5, как при нехватке времени, причина — в `/var/run/xvpn/generate_error` (`xray ports taken by another program: dns_port 10854; …`), xray остаётся на текущем конфиге. `status` показывает её как `error` и тогда, когда reload выполнил не демон (старт, rpcd, триггеры UCI); демон повторяет reload раз в `reload_retry` (п. 6.3) — и после своего reload, и после чужого (`reindex`), и если сам запущен с такой ошибкой. Правила nft (`fw-apply`, `fw-refresh`) берут `tproxy_port` и `dns_port` из индекса работающего конфига, а не из UCI (демон и rpcd так же берут оттуда `api_port`): пока порт занят, трафик и DNS клиентов идут в работающий xray, а не в чужую программу. Если индекса нет (загрузка, `/var` пуст) или в нём нет серверов (тогда порты не проверялись) — xray не запущен, и вместо `full` ставится то же, что без xray (`block` при kill switch, иначе `passthrough`): перенаправлять DNS клиентов на порт чужой программы нельзя. Проверка — снимок перед генерацией: порт, занятый между `generate` и стартом xray, обнаружит п. 6.2.

### 6.6 Серверы вне автоподбора (#60)

`health.no_auto` — список id серверов, которые демон сам не выбирает. Хранится только исключение: по умолчанию сервер участвует, и новые серверы подписки тоже. `best()` пропускает такие серверы так же, как карантинные, но без запасного варианта «из карантина тоже» (`best(true)`). Это действует при старте, при failover, при «список серверов изменился» и при `auto_best`. Тест всех, пинг, карантин и ручной `select` от флага не зависят.

- **Ручной выбор.** `select` пишет id не только в `/etc/xvpn/active`, но и в `/etc/xvpn/active_manual`; выбор демона (`switch_to` из `choose_best`/`rank`) этот файл удаляет. Файл переживает перезапуск демона и сервиса; `generate` при переименовании активного (`moved_from`) переносит и его. Сервер вне автоподбора, выбранный вручную, остается активным, пока отвечает, и `rank` (`auto_best`) его не покидает; ручной выбор сервера из автоподбора `rank` покидает, как раньше. Если выбранный вручную сервер пропал из списка, `switch_to` демона файл не удаляет. Когда сервер возвращается в индекс, `check()` переключается на него обратно (`chosen by hand, back in the list`, не после неудачного reload). Если демон перезапускался, пока сервера не было, `/etc/xvpn/active` по-прежнему указывает на него, и `generate` сразу делает его активным. Выбранный демоном сервер, которому сняли флажок, покидается сразу: `set_auto` зовет `choose_best`, и `check()` тоже.
- **Нет кандидатов.** `no_servers`, в `last_error` причина: `all servers are excluded from auto selection` или `no live servers in auto selection (N excluded)`. Если активный сервер вне автоподбора выбран вручную и в этом тесте ответил, демон остается на нем (`connected`, причина в `last_error`). Мертвый активный ведет себя как раньше: повторный failover на каждом отказе.
- **Активный вне автоподбора, не выбранный вручную.** Это сервер, который демон выбрал раньше, или fallback `generate`: если `/etc/xvpn/active` нет (первый старт) или выбранный сервер пропал, `build_index` делает активным первый сервер списка. `check()` такой сервер не проверяет, а зовет `choose_best`. Пока выбирать не из чего (`no_servers`), повтор идет не чаще `interval × fail_threshold`, как у failover мертвого сервера. xray при этом работает с этим сервером как с маршрутом по умолчанию, как и без живых серверов. Проверка идет после отложенного выбора при неработающем xray (`xray_choose`), чтобы не гонять тест всех на каждом тике, и не идет после неудачного reload (`reload_error`, `reload_pending`): тогда активный — это то, что запущено, а не то, что выбрано (§6.3). Во время ожидания NTP (`waiting_time`) она тоже не идет: выбор откладывается до синхронизации (§6.4).
- **Чтение.** Демон читает `health.no_auto` во время работы: заново, когда у `/etc/config/xvpn` меняются inode, mtime или размер (`uci commit` пишет файл через rename). Так видны и правки через `uci`, и чистка из `generate`.
- **Запись.** ubus `xvpn set_auto {id, auto}` (rpcd `luci.xvpn set_auto` — прокси) пишет UCI курсором демона. Если в `/tmp/.uci` есть чужие незакоммиченные правки `xvpn`, запись отклоняется (`xvpn has uncommitted changes`): `commit` закоммитил бы и их. Курсорный `commit` не шлет `config.change`, поэтому reload-триггер не срабатывает. Если вернуть сервер в автоподбор при `no_servers`, сразу идет `choose_best`.
- **Без перезапусков.** Флаг не попадает в конфиг xray, `index.json` и ключ кэша `tested.json` (`frame` — это `main` и `access`). Поэтому `generate` дает тот же `config.json`, и procd не трогает xray. Демон procd перезапускал по `procd_set_param file /etc/config/xvpn`: любой reload после записи флага (свой `switch_to`, `reload_config` из LuCI) убил бы его вместе с замерами, карантином и идущим тестом. Теперь вместо `file` у инстанса `xvpnd` есть переменная окружения `XVPN_CONF` с md5 от `uci export xvpn` без строк `list no_auto` и `option no_auto`. procd сравнивает env инстанса при reload, а `data` не сравнивает. Любая другая настройка по-прежнему перезапускает демон.
- **Чистка.** `prune` (в `cli.uc generate`, при каждом start/reload) ищет id, которых нет ни в кэшах подписок из UCI (включенных или нет, до фильтров `include`/`exclude`), ни среди ручных ссылок. Флаг переживает выключение подписки и фильтр. Пропавший id удаляется не сразу, а через `NO_AUTO_GRACE` = 7 дней отсутствия: провайдер может временно отдать «заглушку», и плохой сервер молча вернулся бы в автоподбор. Время пропажи хранится в `/etc/xvpn/no_auto_gone.json` (`{id: since}`, файл пишется только при изменениях). Вернувшийся сервер выпадает из файла. Время в будущем (часы перевели назад, NTP после загрузки) начинает отсчет заново. Пропажа и удаление пишутся в лог. Коммит UCI делается только при удалении и не делается при чужих незакоммиченных правках; тогда время пропажи сохраняется.

## 7. nftables

```
table bridge xvpn {
  set ports { type ifname; flags interval; auto-merge;
              elements = { "lan2", "xvpn-ap0", "xvpn-ap0.*" } }        # порты + ifname SSID с маской
  chain pre { type filter hook prerouting priority -210;
              iifname @ports meta mark set meta mark | CLIENT }
}
table inet xvpn {
  set nets     { type ifname; flags interval; auto-merge;
                 elements = { "br-guest", "xvpn-ap0", "xvpn-ap0.*" } }   # сети + ifname SSID с маской
  set bypass4  { type ipv4_addr; flags interval; … RFC1918, CGNAT, loopback, link-local, multicast … }
  set bypass6  { type ipv6_addr; flags interval; ::1, fc00::/7, fe80::/10, ff00::/8 }
  chain mark     { prerouting, mangle-10: iifname @nets → mark |= CLIENT }
  chain tproxy   { prerouting, mangle: не CLIENT → return; dst local → return; dport 53 → return (hijack);
                   bypass → return; ipv6+block → return; tcp/udp → mark |= TPROXY, tproxy to :PORT }
  chain dns      { prerouting, dstnat-5: CLIENT && dport 53 → redirect to :DNS_PORT }
  chain forward  { forward, filter-5: CLIENT && не bypass → reject (kill switch; при ipv6=block — весь IPv6) }
  chain input    { input, filter-5: порты tproxy/dns не от CLIENT/TPROXY → drop }
}
ip rule add fwmark TPROXY/TPROXY table 100 ; ip route add local default dev lo table 100   (и -6)
```

`ip rule` и маршрут нужны только tproxy: они ставятся в `full` до `nft -f` (маршрут без меток безвреден, момента с метками без маршрута нет) и снимаются после перехода в `block`, `passthrough` и `minimal` — в `fw-guard` при загрузке lo ещё не поднят, и `ip route … dev lo` падал бы с «Nexthop device is not up». `ip rule` с fwmark добавляется, только если его нет, а дубли от нечистой остановки удаляются после этого (busybox `ip` не фильтрует `rule list`, поэтому правила считаются по выводу). В `block` в `guard_input` идут только допустимые порты (без дублей): `block` — откат неудавшегося `full`, и неверный `tproxy_port` не должен ронять и его до `minimal`, который не покрывает порты моста и SSID.

Точки доступа → имена устройств (`resolve` в `firewall.uc`, при каждом `fw-*`):
- **Сеть** → L3-устройство и устройство из `network.interface dump` (когда netifd её поднял) плюс `network.<имя>.device` из UCI (до netifd — guard при загрузке); `@алиасы` пропускаются. У Wi-Fi-only сети (без `device`) L3-устройство — сам SSID, поэтому её SSID обрабатываются как выбранные SSID.
- **SSID** → фиксированный `ifname` из UCI (§7.2) и текущий ifname из `network.wireless status` (до того как netifd применил фиксированное имя). Имя SSID попадает и в `bridge @ports` (SSID в мосту: в `inet` iifname — мост), и в `inet @nets` (SSID — сам L3-интерфейс, мост его не видит). Вместе с именем в наборы идёт маска `имя.*`: станции WDS (`xvpn-ap0.sta1`) и динамические VLAN (`xvpn-ap0.5`) — отдельные интерфейсы, без маски их клиенты шли бы мимо VPN. Маска с точкой не задевает чужие имена (`xvpn-ap1.*` не совпадает с `xvpn-ap10`); для имён длиннее 13 символов её нет — подынтерфейс не уложится в 15. Маски — это интервалы, поэтому наборы с `flags interval` и `auto-merge` (имя внутри маски, например `xvpn-ap0.5` в сети, иначе даёт «conflicting intervals»). Fail-closed для SSID с WDS/VLAN отвергнут: эти режимы рабочие, а маска покрывает их без потери функции.
- **Порт** — как есть.

Сервис перезагружается по изменениям `xvpn`, `wireless`, `network`; правила перечитываются без перезагрузки по hotplug: `net`/`add` и `net`/`move` для `DEVTYPE=wlan` (ждёт до 15 с, пока ifname появится в `network.wireless status`) и `iface`/`ifup` для сетей из `access.network`.

Особенности:
- Метка, выставленная в `bridge`-таблице, сохраняется в skb и видна в `inet` prerouting — так один SSID/порт уходит в VPN без выделения отдельной сети.
- ICMP (ping) xray не проксирует: при kill switch пинг из VPN-сети в интернет не проходит — это ожидаемо.
- Flow offloading fw4 (на AX3000T есть аппаратный PPE): TPROXY-трафик доставляется локально и не офлоадится. Потоки, установленные до включения VPN, живут до завершения — UI предупреждает.

### 7.1 Режимы правил и жизненный цикл

| Режим | Что делает | Когда |
|-------|-----------|-------|
| `full` | перехват TPROXY + DNS, kill switch | xray работает (`fw-apply`) |
| `passthrough` | только метки и блок IPv6, клиенты идут напрямую | kill switch выключен и живых серверов нет (демон); `fw-guard` при выключенном kill switch |
| `block` | метки, reject forward в интернет и DNS клиентов к роутеру; без tproxy/fib/nat | `fw-guard` при kill switch; fallback при любой ошибке nft |
| `minimal` | только `inet`: reject forward для `iifname @nets`; отдельные порты и SSID не закрыты | последний fallback, если не принят и `block` (нет `kmod-nft-bridge`) |

Запрошенный режим (`fw_want`) и применённый (`fw_mode`) хранятся отдельно. `fw-refresh` применяет запрошенный, поэтому fallback и ошибка воспроизводятся сами, а `fw_error` удаляется только когда применился именно запрошенный режим. Все `fw-*` (init.d, демон, hotplug, include fw4) берут `/var/lock/xvpn-fw`, запрошенный режим читается уже под блокировкой. Устройства с именем длиннее 15 символов (IFNAMSIZ) отбрасываются с записью в лог: из-за них nft отверг бы весь файл. Без демона состояние правил отдаёт rpcd `luci.xvpn firewall` → `{want, mode, error, warning}` (`warning` — из `fw_warn`, §7.2).

Правила не исчезают, пока сервис включён (`main.enabled=1` и автозапуск `/etc/init.d/xvpn enable`):
- **Загрузка.** `xvpn-guard` (START=18, раньше fw4=19 и network=20) ставит `fw-guard`. `uci-defaults` включает `xvpn-guard` при каждой установке и апгрейде (postinst при апгрейде новые init-скрипты не включает): ручное `disable` действует только до следующего апгрейда. Имена устройств — без netifd: сети из UCI (`network.<имя>.device`), SSID — фиксированные `wireless.<секция>.ifname` (§7.2). `xvpn` (START=95) атомарно заменяет таблицу на `full`. `xvpn-guard start` (в т.ч. из postinst) ничего не делает — работает только `boot`.
- **stop / restart / upgrade / shutdown.** `stop_service` ставит `fw-guard`, `start` — `full`; `nft -f` атомарен, окна без правил нет. Если автозапуск `xvpn` выключен (`/etc/init.d/xvpn disable`) при `enabled=1`, `stop` снимает правила — `restart` даёт окно прямого доступа до `start`.
- **Выключение.** Правила снимаются (`fw-remove`) только при `enabled=0` или выключенном автозапуске; при удалении пакета `default_prerm` сначала делает `disable`, потом `stop`.
- **Ошибка nft (fail-closed).** `nft -f` не применяет файл частично — остаются прежние правила; затем `cli.uc` ставит `block`, пишет ошибку в `fw_error`, демон отдаёт `state: error`. Следующий успешный `fw-*` удаляет `fw_error`.
- **fw4 flush.** `service firewall stop` / `restart` (`fw4 flush`) удаляет все таблицы nft, в том числе наши. Include `firewall.xvpn` (type script, `fw4_compatible`) выполняется после каждого start/reload fw4 и, если есть `fw_want`, а таблицы `inet xvpn` нет, вызывает `fw-refresh`. Между `firewall stop` и следующим `start` правил нет. `postrm` удаляет include.
- **Wi-Fi поднялся позже, перезапуск радио, `wifi down; wifi up`.** У VPN-SSID фиксированное имя, оно в правилах с самого начала (guard берёт его из UCI) и при перезапуске не переходит к другому SSID — окна нет. hotplug `net` для `DEVTYPE=wlan` — `add` (интерфейс создан) и `move` (hostapd переименовал его на месте) — дожидается ifname в `network.wireless status` (до 15 с) и вызывает `fw-refresh`: убирает прежнее имя, которое мог занять другой SSID. Выключенный SSID (`disabled=1` или выключенное радио) остаётся в правилах только под своим фиксированным именем — его не займёт другой SSID.
- **Сеть поднялась.** hotplug `iface`/`ifup` для сети из `access.network` вызывает `fw-refresh`: L3-устройство (pppoe, Wi-Fi-only сеть) могло появиться или смениться.
- **SSID без имени (fail-closed).** Если у включённого VPN-SSID нет ни фиксированного, ни текущего имени (имя длиннее 15 символов, правка `wireless` не закоммичена), его клиентов правила не покрывают: `fw-*` ставит `block` для всех клиентов VPN (при запрошенном `passthrough` — `passthrough`: клиенты и так идут напрямую), пишет `access points not found: wifi "<секция>" (SSID "…") has no interface name` в `fw_error`, демон отдаёт `state: error`. Ошибка снимается следующим `fw-*`, когда имя нашлось или SSID выключен. Несуществующая секция или сеть ошибкой не считается — у неё нет клиентов.

### 7.2 Фиксированные имена SSID в `/etc/config/wireless`

netifd раздаёт имена `phy1-ap0`, `phy1-ap1`… по порядку при каждом запуске радио: имя VPN-SSID неизвестно до подъёма Wi-Fi (загрузка, `wifi up`) и может перейти к другому SSID после перезапуска. Поэтому xvpn меняет конфиг пользователя — только в этом месте:
- **Кому.** Выбранным SSID (`access.wifi`) и SSID Wi-Fi-only сетей из `access.network`. `cli.uc ifnames` (в начале каждого `start`/`reload` `init.d/xvpn`, в т.ч. при `enabled=0`) ставит им `option ifname 'xvpn-apN'` — наименьший свободный N. Своё имя, заданное пользователем (`option ifname` без префикса `xvpn-ap`), не трогается и используется как есть.
- **Пометка.** Секция, получившая имя от xvpn, помечается `option xvpn_ifname '1'`. Снимаются только помеченные имена; если пользователь потом сменил имя на своё (не `xvpn-apN`), удаляется только пометка.
- **Применение.** После `uci commit wireless` — `ubus call network reload` (то же, что `wifi reload`). netifd в 24.10 делает reconf: `hostapd.uc` сопоставляет BSS по хешу конфига и обычно переименовывает интерфейсы на месте (`bss.rename()`) без перезапуска радио; ядро шлёт `ACTION=move`. Переименовываться могут и соседние SSID: если VPN-SSID A (`phy1-ap0`) получил `xvpn-ap0`, домашний B может стать `phy1-ap0`. Поэтому: hotplug `net` реагирует и на `move`, а `ifnames` запускает в фоне `ifnames-wait` — ждёт (до 30 с), пока у всех включённых VPN-SSID в `network.wireless status` не появится фиксированное имя, и делает `fw-refresh`, убирая прежние имена. До этого правила содержат и фиксированное, и текущее имя (кратко в VPN может попасть и соседний SSID — это не утечка). Если hostapd всё же перезапускает радио, его клиенты переподключаются — только при выборе или снятии выбора SSID.
- **Откат.** SSID, снятые с выбора, теряют `xvpn-apN` при следующем `reload` (выбор в LuCI вызывает его сам). `postrm` снимает помеченные имена, но `network reload` не делает: пакет могут удалять через этот же Wi-Fi; прежние имена вернутся при следующем reload сети или перезапуске радио. Если в `wireless` есть чужие незакоммиченные изменения, `postrm` ничего не трогает.
- **Незакоммиченные правки.** Если в `wireless` есть чужие незакоммиченные изменения (`uci changes wireless`), а имена нужно выдать или снять, они не меняются (иначе `commit` закоммитил бы и чужое): предупреждение пишется в лог и в `fw_warn` (rpcd `luci.xvpn firewall` → `warning`), правила работают по текущим именам из netifd. Следующий `reload` после коммита правок снимает предупреждение; `fw-remove` (выключение сервиса) тоже.
- **Только точки доступа.** У Wi-Fi-only сети имена получают только её SSID с `mode` `ap` (или без `mode`); STA-аплинк той же сети (`wwan`) не трогается.

## 8. LuCI

| Вкладка | Содержимое |
|---------|-----------|
| Статус | состояние, активный сервер, пинг, аптайм, трафик через xray; подписки (трафик, срок); таблица серверов (пинг, «Использовать»); кнопки «Проверить все», «Обновить подписки», «Перезапустить», вкл/выкл |
| Подписки | таблица подписок (вкл., имя, URL, интервал, статус, трафик и срок; UA, фильтры, через туннель — в окне правки), «Обновить» у каждой и «Обновить все»; ручные ссылки с проверкой разбора |
| Точки доступа | сети / LAN-порты / SSID флажками, предупреждение о flow offloading; kill switch, перехват DNS и DNS-сервер, IPv6 |
| Настройки | проверка (URL, интервалы, порог, таймаут, авто-лучший, гистерезис, карантин, параллельность), путь к xray, лог-уровень, sniffing, порты, метки, таблица маршрутизации |
| Журнал | `logread` по тегам `xvpn` и xray: фильтр текстом или `/regex/`, источник, «только ошибки», автообновление |

LuCI обращается к демону только через rpcd `luci.xvpn`: uhttpd добавляет к аргументам каждого вызова `ubus_rpc_session`, а ubus-объект на ucode отклоняет аргументы вне своей политики (`INVALID_ARGUMENT`). Поэтому в `luci.xvpn` есть прокси `status` (ответ демона плюс `running: true`; без ответа — `{running: false}`; всегда — `enabled` из UCI и `time` роутера), `test`, `select {id}` и `set_auto {id, auto}`, а в ACL нет объекта `xvpn`. rpcd ждёт демон не дольше 2 с (`connect(null, 2)`): зависший xvpnd не должен останавливать rpcd, а с ним и весь LuCI. Таймаут (ubus-код 7: демон есть, но занят или завис) отличается от отсутствия демона: `status` добавляет `timeout: true`, а `test`, `select` и `update` возвращают ошибку `timeout` вместо `not running` — действие могло и выполниться; `update` при таймауте не запускает `cli.uc update` сам. Аптайм, «N назад» и скорость считаются от `time` роутера, а не от часов браузера.

Вкладка «Статус» каждые 5 с (`poll`) вызывает `status`, `subscriptions {updating: false}` (флаг берётся из `status`), `firewall` и, только без демона, `servers`. `stats` не запускает xray: rpcd читает счётчики outbound из секции `metrics` (`curl -m 2 http://127.0.0.1:<api_port>/debug/vars`, §6.4), поэтому вызывается часто — раз в 10 с (не на каждом опросе: зависший xray держал бы rpcd секунду таймаута, пока демон не выставит `xray_down`), только при работающем и включённом сервисе и не в `xray_down` (иначе rpcd ждал бы таймаута запроса); скорость — средняя между замерами. Страница перерисовывается целиком, но узлы кнопок и фокус сохраняются (кнопки серверов, ушедших из списка, выбрасываются), а при выделенном тексте перерисовка пропускается. Демон не ответил за 2 с — «демон не отвечает», а не «не запущен». «Отключить» и «Перезапустить» — с подтверждением. Неизвестное состояние демона показывается как есть. Флажок «Auto» у каждого сервера зовет `set_auto` (§6.6); без демона он выключен, а его значение берется из `servers` (`auto`). Как и кнопки, флажки переживают перерисовку: пока вызов идет, флажок выключен и показывает новое значение.

Вкладка «Подписки» — `form.Map` над `xvpn`: `GridSection` секций `subscription` и `NamedSection` `manual`. Id подписки — имя её секции, под ним лежат кэш (`/etc/xvpn/subs/<sid>.json`) и статус (`/var/run/xvpn/sub-<sid>.json`). Имя анонимной секции зависит от её позиции: при перетаскивании или удалении подписки выше по списку оно меняется, а кэш и статус остались бы под старым. Поэтому новые подписки создаются именованными секциями `sub_<8 hex>`, а `uci-defaults` переименовывает старые анонимные (по одной, с коммитом после каждой) и переносит их кэш и статус. Кэш и статус подписок, которых больше нет в UCI, удаляет `cli.uc generate` (при каждом start/reload). curl качает подписку только по http/https, в том числе после редиректа. Статус каждой подписки (серверов, пропущено, формат, когда обновлена и как — через туннель или напрямую, ошибка, следующее обновление, profile-title) и трафик со сроком из `subscription-userinfo` берутся из `luci.xvpn subscriptions` и каждые 5 с обновляются в ячейках таблицы, не трогая форму. «Обновить» у подписки и «Обновить все» зовут `luci.xvpn update {sid}` и `update` без аргументов (`{"sid": null}` политика rpcd отклоняет) — только через демон, §6.1; пока идёт обновление, кнопки выключены, у неприменённой подписки — тоже. URL — http/https, не длиннее 2048 символов, записывается без пробелов по краям. Ручные ссылки — `textarea` по ссылке на строку (в UCI — `list link`); каждую строку разбирает `luci.xvpn parse_links` тем же `parse_link`, что и бэкенд (ответ без outbound — в нём учётные данные): под полем таблица — протокол, имя, адрес, ошибка или «дубликат строки N». Сохранить нельзя, пока есть ошибка разбора или строка без ответа проверки; если проверка не удалась (ошибка rpcd), повтор — только после правки текста. Имена, profile-title и ошибки выводятся только текстовыми узлами. Подпись состояния `error` и баннер `fw_error` зависят от применённого режима из `firewall`: `block`/`minimal` — клиенты VPN заблокированы, `passthrough` — идут напрямую; `fw_error` выводится с переносами строк, `warning` (из `fw_warn`, §7.2) — предупреждением.

Вкладка «Точки доступа» — `form.Map` над секцией `access`. Сети, порты и SSID берутся из `luci.xvpn access_points` (сети — `network.interface` без `loopback` и `wan*`; порты — `ports` мостов; SSID — `wifi-iface` в режиме AP с SSID, радио, диапазоном, сетью, `disabled` и текущим `ifname`, чтобы показать выданный `xvpn-apN`) и выводятся флажками со своим виджетом (`ui.Select` с `widget: 'checkbox'` возвращает только одно значение); SSID, имена и прочее из конфигов — только текстовыми узлами. Имя из `access`, которого на роутере больше нет, остаётся в списке с пометкой «not found» и не теряется при сохранении; снятое — пропадает из списка после сохранения. Описание SSID говорит, что выбор и снятие делают `network reload` (клиенты Wi-Fi могут переподключиться) и что SSID получает `xvpn-apN` (§7.2). При `flow_offloading`/`flow_offloading_hw` в `firewall.@defaults[0]` — предупреждение (§7). DNS-сервер — IPv4/IPv6, имя хоста или URL `https://`/`tcp://` со схемой в нижнем регистре. `dns_server()` в `util.uc` берёт как есть любое значение без `://` (UI дополнительно проверяет синтаксис IP и имени хоста), а другие схемы и схемы в другом регистре молча заменяет умолчанием — UI их отвергает.

Вкладка «Настройки» — `form.Map` над `main` и `health`; пустое поле — умолчание из `load_config()`. Числа — целые десятичные или hex с `0x`, как их читает `load_config()` (`hex()` после `0x`, иначе `int()`, который принял бы и «12abc» — UI такое отвергает), в диапазонах: интервал 5–3600 с и больше таймаута (1–60 с), порог 1–100, фоновый тест 60–86400 с, карантин 0–86400 с, параллельность 1–64, гистерезис 0–10000 мс. Порты 1–65535, попарно разные и вне диапазона тестовых `test_port_base … +N−1`, где N — число серверов из `luci.xvpn servers`; сам диапазон должен уместиться до 65535. Метки — 1…0xffffffff (hex или десятичные) без общих битов (правила проверяют `mark & m == m`). Таблица маршрутизации — не 253–255. Гистерезис виден только при «авто-лучшем», но при скрытии не удаляется (`retain`). Служебные опции для тестов (`reload_idle`, `reload_retry`, `generate_budget`, §6.3) в UI не выводятся. Демон перечитывает настройки при перезапуске: procd перезапускает его по изменению `/etc/config/xvpn` без `health.no_auto` (env `XVPN_CONF`, §6.6).

Вкладка «Журнал» вызывает `luci.xvpn log` — до 300 последних строк из последних 2000 строк `logread -l`, отобранных `grep -E` по тегу: `xvpn` (скрипты и `logger` демона), `ucode` (stdout/stderr самого xvpnd под procd, в т.ч. трассы `die()`) и имя бинаря xray (`basename main.xray_bin`, под ним procd пишет его вывод). По тегу, а не по подстроке: «xvpn» встречается и в чужих строках (URL LuCI в журнале uhttpd). `logread -e` не годится — он берёт базовый regex, и `xvpn|xray` не совпадает ни с чем. rpcd однопоточный и, пока ждёт `logread`, не отвечает никому, а `logread` ждёт logd: зависший `logread` убивается через 3 с (в busybox нет `timeout` — `kill` из фоновой подоболочки), поэтому вкладка обновляется раз в 10 с. Фильтры работают в браузере; вид остаётся внизу, только если был внизу, а при выделенном в журнале тексте обновление пропускается. Строки выводятся через `textContent`.

## 9. Сборка и тесты

- Тесты (docker, образ `openwrt/rootfs:x86-64-24.10.4`): `scripts/test.sh` — парсер ссылок/подписок, генерация конфига, `xray run -test` на сгенерированном конфиге, рендер nft (все режимы) и `nft -c` (проверка синтаксиса), резолв сетей и SSID (UCI до netifd, живые имена, SSID в обоих наборах), фиксированные имена SSID (выдача, повторный запуск без изменений, откат при снятии выбора, своё имя пользователя, незакоммиченные правки), ошибка для SSID без имени, пометка `xvpn_ifname` (непомеченное `xvpn-ap0` не снимается), STA не получает имя, маски `имя.*` (нет маски для длинных имён), `ifnames_applied`, предупреждение при незакоммиченных правках; `nft -c` с маской, перекрывающей точное имя.
- Интеграционный тест `scripts/itest.sh` (procd в контейнере, `NAME=` для параллельных запусков): выбор сервера, failover, подписка; серверы вне автоподбора (§6.6; третий сервер быстрее остальных, у их remote — freedom `fragment`): снятый флажок у сервера, выбранного демоном, сразу уводит на другой без перезапуска xvpnd; failover при живом выключенном и более быстром сервере уходит на медленный из автоподбора; выключенный не выбирается ни при failover, ни при старте без `/etc/xvpn/active` (`no_servers` с причиной); выбранный вручную остается после снятия флажка, `reload_config` (PID xray и xvpnd те же) и рестарта сервиса, при его отказе failover уходит на сервер из автоподбора; зависший xray (`kill -STOP`) и битый `xray_bin` → `xray_down` без карантина и passthrough, перезапуск, отказ после трёх и восстановление после починки бинаря без перезапуска демона; зависший reload (`sleep` в `start_service`, чужой лок procd через `flock`): `select` — `busy`, через `reload_idle` (в itest 15 с) `state: error`, `sleep` убит, активный сервер по-прежнему проверяется, `test` — `busy`, затем повтор и `connected`; медленный `xray_bin` (`-test` по 4 с, один сервер отвергнут) — `generate` ~35 с, дольше `reload_idle`, не убивается; старт без флага синхронизации времени (часы контейнера не поменять: «неверные часы» — остановленный сервер, `system.ntp` задан, sysntpd не запущен) → `waiting_time`, карантина нет, с kill switch клиент заблокирован, без него — passthrough; `test` — `busy`; `hotplug-call ntp` со `stratum=16` ничего не меняет, со `stratum=2` → `connected`; без события — работа дальше через `time_wait` (в itest 20 с), перезапуск во время ожидания срок не продлевает; `generate`, убитый посередине, не меняет `config.json` и `index.json`; `stats` (счётчики трафика активного) и повторный reload с теми же серверами не запускают xray (обёртка `xray_bin` считает запуски), другой бинарь тестируется один раз; клиент в netns за портом моста и «интернет» в другом netns, fw4 запущен — туннель работает, прямого трафика нет при загрузке (guard), restart, stop, сломанном `nft` (fallback из passthrough, `state: error`, `fw-refresh` сохраняет ошибку, `minimal` без bridge); правила возвращаются после fw4 flush; SSID получают `xvpn-apN` (без радио — имена только из UCI) и попадают в оба набора, SSID без имени → `block` и `state: error`, при `passthrough` — клиенты напрямую и ошибка, выключенный — без ошибки; фоновое ожидание имён после выдачи; порт клиента, переименованный после правил в `xvpn-ap0` и `xvpn-ap0.sta1`, идёт в туннель, а `xvpn-ap10` — нет; hotplug `net` с `ACTION=add|move`; предупреждение и отказ от коммита при чужих правках `wireless` (и в `postrm`); `ifup` VPN-сети перечитывает правила; снятие выбора и `postrm` возвращают имена; `fw-remove` ждёт блокировку; правила снимаются при `enabled=0` и `disable`.
- LuCI для ручной проверки вкладок: `scripts/luci.sh` (procd в контейнере, `luci` + пакет из рабочей копии, два локальных VLESS-сервера — живой и мёртвый — и подписка с `subscription-userinfo` через CGI uhttpd) → http://127.0.0.1:8019, root / тестовый пароль из скрипта; `sync` — скопировать файлы пакета заново (с сохранением `/etc/config/xvpn`), `stop` — удалить контейнер. Переменные: `DOCKER` (по умолчанию `docker --context default`), `NAME`, `PORT`, `PASS`. `/etc/rc.d/S11sysctl` удаляется до `/sbin/init`: в `--privileged`-контейнере он менял бы sysctl хоста.
- Сборка ipk (docker, `openwrt/sdk:mediatek-filogic-24.10.4`): `scripts/build.sh` → `dist/luci-app-xvpn_*.ipk` (и `luci-i18n-xvpn-*.ipk`, когда появятся po-файлы). Из фида luci (ветка `openwrt-24.10`) берутся только `luci.mk`, `luci-base` и `csstidy`, и собираются лишь их host-утилиты; сам пакет собирается с `NO_DEPS=1` — иначе SDK компилировал бы все рантайм-зависимости (luci-base, xray-core вместе с Go), а пакету архитектуры `all` они нужны только в `Depends`. Пакет архитектуры `all`, так что SDK под другую архитектуру тоже подошёл бы. Переменные: `DOCKER` (по умолчанию `docker --context default`), `IMAGE`, `LUCI_FEED`.
- `XRAY_BIN=<путь к бинарю xray>` в `scripts/test.sh` проверяет конфиг этой сборкой вместо xray-core из фида.
- CI — локальный, `scripts/ci.sh` (GitHub Actions не используется): проверяет чистый экспорт HEAD (`git archive` в `.ci/src`, незакоммиченные изменения не проверяются) и выполняется перед каждым push и PR. Шаги по очереди, лог каждого — `.ci/<шаг>.log`: `test` — `test.sh` с xray из фида; `test-latest` — `test.sh` с последним релизом xray с GitHub (sha256 сверяется по `.dgst`; пока только предупреждает, см. #14); `itest` — `itest.sh`, через 12 мин убивается с состоянием контейнера в логе; `build` — `build.sh`, ipk копируются в `dist/`. Контейнер itest по умолчанию называется по хэшу пути checkout (`NAME`), так что worktree не мешают друг другу. `DOCKER` по умолчанию `docker --context default`. `itest.sh` удаляет `S11sysctl` до запуска `/sbin/init`: в privileged-контейнере он записал бы sysctl хоста (`kernel.panic`, `core_pattern`). Все `ubus call` в itest ограничены `-t 5`, ожидания — дедлайном по часам; при `TIMEOUT` печатаются `xvpn status`, `service list`, список зависших вызовов и хвост `logread`.
- Релиз: тег `v<PKG_VERSION>` (при `PKG_RELEASE:=1`) или `v<PKG_VERSION>-r<PKG_RELEASE>`, например `v0.1.0`, `v0.1.0-r2`. `sh scripts/ci.sh release` берёт тег из Makefile, требует чистое дерево и HEAD = `origin/main`, отказывает, если тег уже есть; после зелёных `test`/`itest`/`build` ставит аннотированный тег, пушит его и публикует GitHub Release с ipk (`gh release create --generate-notes`). Pre-release-теги (`v0.2.0-rc1`) не поддерживаются. Сборка берёт голову ветки `openwrt-24.10` фида luci (`luci.mk`, host-утилиты luci-base/csstidy), а не зафиксированный коммит: ipk одного тега, собранный в разные дни, может немного отличаться; для точного воспроизведения — `LUCI_FEED='https://github.com/openwrt/luci.git^<коммит>'`.

### Чек-лист проверки на AX3000T
1. Установка ipk тянет `xray-core`, `kmod-nft-tproxy`, `kmod-nft-socket`, `kmod-nft-bridge`, `curl`.
2. Добавить подписку → «Обновить» → серверы с пингами на вкладке «Статус».
3. Выбрать SSID и порт `lan2`, включить → с клиента на этом SSID/порту `curl ifconfig.me` = IP VPN-сервера; на `lan1` — IP провайдера.
4. `killall xray` → у клиентов VPN нет интернета (не утечка), procd поднимает xray за секунды. `killall -STOP xray` → на «Статусе» `xray_down`, через ~30–60 с демон перезапускает xray, серверы не в карантине.
5. `nft add rule inet fw4 output ip daddr <IP активного> drop` → через ~90 с переход на другой сервер.
6. dnsleaktest.com с клиента VPN — только DNS со стороны туннеля.
7. test-ipv6.com — IPv6 недоступен (режим block), утечки нет.
8. Перезагрузка роутера без доступа к подписке → VPN поднимается из кэша.
9. С клиента VPN-SSID `ping -i 0.2 1.1.1.1` во время `reboot`, `service xvpn restart`, `wifi down; wifi up` и перезапуска радио из LuCI — ни одного ответа (ICMP не туннелируется, ответ = утечка). `iw dev` — у VPN-SSID имя `xvpn-apN`.
10. `nft` без `kmod-nft-tproxy` (или испорченный `tproxy_port`) → клиенты без интернета, на «Статусе» ошибка.

## 10. Ограничения v1
- Только полный туннель (раздельная маршрутизация — в идеях).
- Трафик самого роутера в VPN не идёт.
- DNS клиентов VPN идёт на один `dns_server` через туннель — локальные имена (`*.lan`) у них не резолвятся.
- Серверы, которые не пускают к IP-адресам назначения (проверено на AX3000T с подпиской из 18 серверов, 2026-10-27: к IP не пропускал ни один), работают только по домену: sniffing (`main.sniffing`, по умолчанию `1`) подставляет домен из HTTP/TLS/QUIC, DNS идёт DoH по домену (`dns_server` — URL), запросы не A/AAAA (TXT, HTTPS) отбрасываются. `dns_server` — IP или хост (`<dns_server>:53` через туннель), `https://` или `tcp://` (DNS-модуль); прочие схемы xray (`https+local://`, `quic+local://`) ходили бы с роутера напрямую — вместо них берётся значение по умолчанию. С `dns_hijack=0` DNS клиентов идёт в tproxy как обычный UDP по IP и через такие серверы не пройдёт. Прочий UDP и TCP без домена (игры, VoIP по IP) через такие серверы не пройдёт. Health-check ходит по домену (`socks5h`) и этого не видит.
- xray 25.1.30: нет VLESS `encryption` (ML-KEM), hysteria2, TUN. Решается подменой бинаря (`main.xray_bin`).
